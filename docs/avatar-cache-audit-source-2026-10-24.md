После перехода NativeChatAvatars стоит упростить до выбора отправителя и контекста чата, убрав хранение QPixmap. Его полезная роль шире самого кэша: он сохраняет различие обычного контакта и MUC private chat, фильтрует события и предотвращает повторное сканирование ростера.

**Текущая схема кэширования**

| **Уровень**                                    | **Что хранит**                               | **Время жизни и ограничения**                                                                           |
| ---------------------------------------------- | -------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| FileCache, от которого наследуется AvatarCache | Байты изображений по хэшу, metadata привязок | Дисковый кэш; для аватаров задаётся неделя. Используемые записи защищаются от удаления в текущей сессии |
| AvatarCache::jidToIcons                        | Привязки JID к custom/PEP/vCard изображениям | Общий singleton, без account ID в ключе                                                                 |
| AvatarCache::iconset\_                         | Декодированные успешные изображения          | Нет явного лимита, TTL или очистки при выходе из MUC                                                    |
| VCardFactory для контактов                     | Небольшой RAM-кэш и XML на диске             | RAM-кэш примерно на шесть записей; дисковые промахи не запоминаются                                     |
| VCardFactory для MUC                           | vCard по комнате и нику                      | **Три vCard на комнату**; вытеснение по очереди добавления, не LRU. Общего ограничения числа комнат нет |
| NativeChatAvatars                              | Копии успешных и пустых QPixmap              | До закрытия окна, изменения peer или подходящего avatarChanged; MUC-словарь не ограничен                |

Основные реализации: AvatarCache и его структуры, FileCache и значения лимитов, VCardFactory, NativeChatAvatars.

Важно: значения FileCache **1 MiB RAM / 50 MiB disk не ограничивают память&#x20;**&#x69;conset\_**&#x20;и&#x20;**&#x4E;ativeChatAvatars. Декодированные пиксели живут отдельно.

**Что действительно повторяется при пустом результате**

В getMucAvatar() выполняются:

1. Получение full JID и создание строки avatars/\<full-jid>.
2. Поиск в iconset\_.
3. Поиск в jidToIcons.
4. При отсутствии изображения — поиск комнаты в QMap и ника во вложенном QHash VCardFactory.
5. Проверка vCard и фотографии.

Сам mucVcard() делает копию вложенного QHash, но она **implicitly shared**: глубокого копирования трёх vCard при чтении нет. Это лишняя операция с общим объектом, но не копирование всего содержимого. Реализация.

При настоящем отсутствии фотографии **изображение не декодируется**. Повторное декодирование возникает при повреждённых данных, восстановлении производного изображения или после инвалидации.

Для обычных контактов ситуация потенциально дороже: vcard() после промаха RAM обращается к XML-файлу. Отсутствующий файл проверяется заново при следующем вызове.

Эти getters сами не запускают сетевые запросы. Подгрузка вызывается обработкой presence/PEP и явными запросами vCard.

Кроме нативного чата, ими пользуются ростер, MUC user model, tooltip, уведомления, InfoDlg, передача файлов и плагины. Например, ростер, MUC user model, pluginmanager. Центральный negative cache помог бы всем этим потребителям.

**Пустой QPixmap сейчас объединяет разные состояния**

| **Состояние**                  | **Что можно узнать в текущем коде**                                                 |
| ------------------------------ | ----------------------------------------------------------------------------------- |
| Информация ещё неизвестна      | Промах vCard-кэша виден внутри resolver, но наружу возвращается null                |
| Фото подтверждённо отсутствует | Успешно полученная vCard без PHOTO либо явное удаление источника                    |
| Загрузка идёт                  | Известно очереди запросов, но AvatarCache не хранит полноценного состояния загрузки |
| Данные повреждены              | Определяется при декодировании; наружу снова null                                   |
| Фото удалено                   | Видно по входящему событию, но отдельное состояние отсутствия не сохраняется        |
| Источник временно недоступен   | Ошибка известна запросу; до AvatarCache она не доходит как отдельный результат      |

Есть и дополнительный случай: **PHOTO существует как URI, но встроенных байтов нет**. Это тоже нельзя объявлять отсутствием фотографии.

OpResult::NoData не решает эту задачу: он используется и для отсутствующего содержимого по хэшу, и для неподходящих/повреждённых данных.

Протокол также различает неизвестность и отсутствие: пустой update-элемент XEP-0153 означает «ещё не готов объявить изображение», а пустой \<photo/> — отсутствие объявляемого изображения. Их нельзя объединять в один постоянный negative result. [XEP-0153](https://xmpp.org/extensions/xep-0153.html#bizrules-presence).

**Обнаруженные дефекты, которые нужно исправить раньше negative cache**

- **Первое чтение vCard с диска возвращает пустой объект.** После успешного чтения вызывается checkLimit(), затем выполняется безусловный return {}. Следующий вызов уже найдёт объект в RAM. NativeChatAvatars может запомнить первый пустой результат до следующего сигнала. vcardfactory.cpp:220.
- **Удалённое фото может восстановиться из старой vCard.** Пустой photo hash удаляет изображение из AvatarCache, но VCardFactory может продолжать хранить старое PHOTO. Следующий getter импортирует его обратно. Условие воспроизведения: старая vCard ещё находится в кэше, изображение не перекрыто другим источником. Удаление, повторный импорт.
- **Аккаунты не разделены.** jidToIcons, iconset\_, MUC-vCard-кэш и очередь vCard-запросов не включают account ID. Очередь даже объединяет запросы разных аккаунтов и выбирает подключённый аккаунт для исполнения. Это существующее свойство архитектуры, а не новая проблема предлагаемого negative cache. Ключи AvatarCache, очередь.
- setPhoto()**&#x20;требует отдельного исправления или объяснения тестом:** переданные байты сейчас не устанавливаются; вызывается setPhoto(UriValue{}). vcardfactory.cpp:263.

Это выводы из анализа конкретных путей кода. Сценарии удаления/reconnect с настоящим сервером в рамках аудита не запускались.

**Рекомендуемая архитектура**

Оставить общий FileCache для содержимого по хэшу. JID-привязки и результаты разрешения хранить в AvatarCache с ключом:

account ID + тип contact/MUC + нормализованный bare/full JID.

Внутри того же AvatarCache:

- Сохранить существующий положительный кэш.
- Добавить ограниченный QCache отрицательных результатов.
- Хранить причину null: Unknown, NoPhoto, Fetching, InvalidImage, Unavailable.
- Инвалидировать по событиям источника, даже когда раньше изображения вообще не было.
- Согласованно сбрасывать vCard, привязку и memo при смене личности за MUC-ником.
- Не принимать поздний ответ запроса из предыдущего поколения комнаты/участника.

Для ограничения памяти достаточно начать с **одного лимита, например 4096 negative entries, и одного ленивого TTL, например 30 секунд**. Это стартовые параметры, не протокольные гарантии.

TTL проверяется при обращении. Он не запускает запросы и не вызывает периодическую перерисовку. Основное обновление — существующие события; TTL лишь ограничивает жизнь ошибочного локального предположения. Отдельный polling не нужен; XEP-0153 прямо запрещает опрашивать vCard ради обнаружения нового аватара. [XEP-0153](https://xmpp.org/extensions/xep-0153.html#bizrules-download).

Не рекомендую добавлять пустые PsiIcon в существующий бесконечный iconset\_: это не решает ограничения размера и усложняет правильное удаление отрицательных записей.

Сам iconset\_ пока удалять нельзя: tooltip генерирует \<icon name="avatars/...">, а WebEngine использует hash/data API. Потребитель iconset.

Обязательные регрессии: первое появление фото после null; удаление без восстановления; вытеснение четвёртой MUC-vCard; повреждённые данные; timeout и последующее успешное получение; Silent; смена/повторное использование ника; reconnect; поздний старый ответ; два аккаунта с одинаковым JID; TTL и лимит; tooltip, WebEngine и плагины.
